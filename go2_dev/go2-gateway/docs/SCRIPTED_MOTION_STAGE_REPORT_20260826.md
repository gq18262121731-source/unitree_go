## 1. 报告信息

- 日期：2026-08-26

2026-08-26 后续补充：无线 SDK2 DDS 四组合失败后，比赛候选链路切换为 WebRTC DataChannel。WebRTC 已完成 ReadOnly、Stop/零速度和 `0.23 m/s × 0.40 s` 极短前进脉冲三级 Gate，运动 transport 判定通过；正式 `WebRTCMotionBackend`、Companion、UWB 与 LiDAR 无线闭环仍未实现或验收。

## 2. 阶段目标与实现结果

本阶段目标是在不改变现有 Companion/伴随控制链路的前提下，增加一套 PC 端 Python 动作编排能力，并将动作内容、运动控制参数和真实执行链路分离：

```text
configs/phone_demo.yaml
        ↓
MotionActionDispatcher
        ↓
ScriptedMotionController
        ↓
RobotService / UnitreeAdapter
        ↓
SportClient
```

已经完成：

1. `ScriptedMotionController` 提供前进、后退、左右横移、左右旋转、等待和停止等目标式接口。
2. 平移使用 `SportModeState.position` 在动作起始局部坐标系中计算闭环进度。
3. 旋转使用 `imu_state.rpy[2]` 和跨 ±π 累计角度计算闭环进度。
4. 动作目标及顺序放在 `configs/phone_demo.yaml`，速度、容差、减速和超时放在 `configs/scripted_motion.yaml`。
5. 所有真实动作统一经过既有 `RobotService / UnitreeAdapter / SportClient` 链路，不在 demo 脚本中直接散落 `Move + sleep`。
6. 保留独占 Writer、状态新鲜度、动作超时、停滞检测、速度硬限幅、异常停止、`KeyboardInterrupt` 停止和动作结束 `StopMove`。
7. 默认禁用纯时间估算回退，位置或航向闭环不可用时不把时间估算伪装成真实里程。

一次短时 `verify_state.py` 运行曾出现 `SPORT_STATE_TIMEOUT`，随后独立 DDS 诊断在同一 `eth0`/Domain 0 上成功收到 `SportModeState` 65 个样本和 `LowState` 102 个样本。因此本阶段将其记录为短采样窗口内的一次瞬时超时，而不是持续性 DDS 故障。

当前结论只适用于已经验证的有线链路。无线 SDK2 DDS/SportClient 运动控制尚未验证，不能据此认定拔掉网线后仍可运行本脚本。

## 4. 当前运动参数

`configs/scripted_motion.yaml` 当前有效参数如下：

| 参数 | 当前值 | 依据 |
|---|---:|---|
| 前进速度 | 0.30 m/s | 0.23 m/s 方案较慢，减速后曾停顿/扭动 |
| 后退速度 | 0.18 m/s | 0.10 m 真机后退通过 |
| 横移速度 | 0.30 m/s | 0.18 m/s 未形成有效横移步态 |
| 旋转速度 | 0.60 rad/s | 分级批准并通过 30°、90° 真机复测 |
| 近目标前进速度 | 0.23 m/s | 已形成稳定前进步态 |
| 近目标横移速度 | 0.30 m/s | 避免低速只产生身体侧移 |
| 近目标旋转速度 | 0.50 rad/s | 最后 20° 使用已验证稳定速度 |
| 距离容差 | 0.025 m | 当前小范围平移结果均在容差内完成 |
| 角度容差 | 2.0° | 30°、90° 当前结果均在容差内 |
| 控制频率 | 5 Hz | 通过既有服务持续刷新速度命令 |
| 状态超时 | 0.50 s | 陈旧状态触发停止 |
| 时间回退 | 禁用 | 只接受真实位姿闭环结果 |

网关硬限幅同步为：`VX=0.30 m/s`、`VY=0.30 m/s`、`WZ=0.60 rad/s`。这些是 scripted motion 的批准上限；Companion/Follow 仍保持 `vy=0`，其 yaw 上限仍为 0.30 rad/s。

## 5. 调参过程中的失败证据

失败试验被保留为调参依据，未重复使用同一失败参数盲目扩大测试距离。

| 试验 | 参数 | 软件结果 | 现场表现 | 处置 |
|---|---:|---|---|---|
| 左转 30° 初测 | 0.28 rad/s | 仅累计 8.079°，5.84 s 超时 | 未形成正常转向步态，主要表现为身体扭动 | 经批准提高至 0.50，之后再分级提高至 0.60 rad/s |
| 右横移 0.20 m 初测 | 0.18 m/s | 仅累计 0.0284 m，4.24 s 超时 | 未形成正常横移步态 | 经批准将横移提高至 0.30 m/s |
| 前进 0.80 m 初调 | 0.23→0.20 m/s | 0.7987 m，7.04 s，闭环完成 | 0.67–0.72 m 附近明显停顿或扭动 | 经批准改为 0.30→0.23 m/s |

这些记录说明 Go2 的可用步态存在最低有效指令区间。过低速度并不必然更平稳，可能只产生姿态变化而不能形成连续步态。

## 7. 安全与兼容性结论

本阶段确认：

1. 每个动作独立完成后才进入下一个动作，动作结束会执行 `StopMove`。
2. 已执行动作均能够及时停车，且现场逐项确认原厂遥控器可以接管。
3. CLI 要求 Companion 为 `IDLE`，并要求输入独占 Writer 与开放场地确认词。
4. scripted motion 通过统一服务层执行，没有为各 demo 新建彼此独立的运动 Writer 逻辑。
5. 本阶段软件回归测试曾达到 514 项通过，且 Python 编译检查通过；未发现对现有伴随链路的软件回归。

“未发现软件回归”不等于已经重新完成整套 Companion 真机伴随验收。完整演示前仍应保持 Companion `IDLE`，不得与伴随、其他 SDK 运动工具或网关运动接口并发运行。

## 9. 阶段判定与下一闸门

### 阶段判定

**通过：PC 端闭环单动作、参数分离、统一执行链路和分级真机调参。**

通过范围包括：前进、后退、左右横移、左转 30°/90°、停止和遥控器接管。当前参数可以作为完整序列首次受控测试的基线。

### 下一阶段进入条件

完整序列测试前必须同时满足：

- 至少约 5 m × 5 m 的平整无障碍区域；
- 原厂遥控器在操作员手中并已确认可以接管；
- Companion lifecycle 为 `IDLE`；
- 不存在其他 `SportClient`/SDK 运动 Writer；
- 有线 `eth0`、路由、Ping、DDS 状态正常；
- 操作员了解 `Ctrl+C` 会触发停止清理；
- 首次完整序列由现场人员持续观察，不无人值守运行。

满足条件后，下一阶段命令为：

```bash
python3 tools/go2_motion_demo.py \
  --demo phone_demo --allow-phone-demo --execute
```

需要依次输入：

```text
EXCLUSIVE_MOTION_WRITER
OPEN_AREA_REMOTE_READY
PHONE_DEMO_APPROVED
```

完整序列结束后，应保存逐动作 JSON、失败步骤（如有）、整段用时、现场轨迹偏差、停车情况和遥控器接管结果，再决定是否进入正式演示验收。
